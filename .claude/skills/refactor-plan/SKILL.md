---

## 절차

### Step 1. 목표 확인

사용자에게 아래 세 가지를 물어본다 (한 번에):

1. **리팩토링 목표** — 무엇을 개선하려는가?
2. **도메인 목록** — 어떤 영역을 다루는가? (예: 보안, 프론트엔드, 백엔드, CI/CD)
3. **추가 실행 원칙** — 아래 기본 원칙 외에 더 지켜야 할 원칙이 있는가?
   - 기능 파괴 없이 점진적으로 진행한다.
   - 목표 중심으로 유효성 검사를 확실하게 하고, 안정성을 최우선으로 한다.

도메인 목록을 모르거나 불명확한 경우: opus 모델의 code-explorer로 코드베이스를 탐색해 도메인 후보를 제안하고 사용자가 확정한다.

답변을 받은 후 리팩토링 목표에서 계획 제목을 도출해 확정한다.

---

### Step 2. 코드베이스 탐색

탐색은 세 단계로 진행한다. 각 단계 결과를 다음 단계에 반드시 활용한다.

#### 2-A. 의존 관계 분석 (Dependency-First)

Grep으로 import/dependency 패턴을 스캔해 파일 간 의존 그래프를 파악한다.

기준은 코드베이스 내 분포 기반으로 판단한다: 전체 파일 중 import 수 상위 20% = Fan-out/Fan-in "높음"

- **Fan-out이 높은 파일** — 많은 파일을 참조함 → 변경 시 파급 범위가 큼 → Phase 후반부에 배치
- **Fan-in이 높은 파일** — 많은 파일에 의해 참조됨 → 변경 시 영향받는 곳이 많음 → 신중하게 처리

산출물: `고위험 파일 목록` + `도메인 간 선행/후행 관계` → `analysis/dependency.md`에 저장

#### 2-B. Hotspot 분석 (Evidence-First)

git 히스토리와 복잡도를 교차해 실제로 문제인 파일을 찾는다.

```bash
# 변경 빈도 상위 30개 파일
git log --name-only --pretty=format: | grep -v '^$' | sort | uniq -c | sort -rn | head -30
```

기준은 절대값이 아닌 **해당 코드베이스 내 분포 기반**으로 판단한다.
- 변경 빈도: 추출한 상위 30개 파일 안에서 상위 1/3 = 높음, 중간 1/3 = 중간, 하위 1/3 = 낮음
- 라인 수: 전체 파일 중 상위 20% = 많음

| 변경 빈도 | 라인 수 | 판정 |
|---------|--------|------|
| 높음 | 많음 | Hotspot — 최우선 리팩토링 대상 |
| 높음 | 적음 | 자주 수정되는 설정/유틸 — 주의 필요 |
| 중간 | 많음 | 잠재적 위험 — 중간 우선순위로 처리 |
| 중간 | 적음 | 일반 파일 — 도메인 필요 시 처리 |
| 낮음 | 많음 | 복잡하지만 안정적 — 낮은 우선순위 |

**git 히스토리가 부족하거나 신규 프로젝트인 경우**: 변경 빈도 대신 아래 정적 지표로 대체한다.
- 라인 수 상위 파일 (복잡도 프록시)
- 중첩 깊이가 과도한 파일 (if/for 3단 이상)
- 하나의 파일에 책임이 여러 개인 패턴 (God Class, 1000줄 이상 파일 등)

산출물: `Hotspot 목록` + `도메인별 우선순위` → `analysis/hotspots.md`에 저장

#### 2-C. 도메인 세부 탐색 (Domain-First)

2-A, 2-B 결과를 바탕으로 각 도메인을 code-explorer로 **병렬** 탐색한다.

- 탐색 시작 전 `analysis/dependency.md`, `analysis/hotspots.md`를 에이전트에게 명시적으로 전달한다
- 도메인 수 3개 이상이면 반드시 병렬 실행, 2개 이하이면 직접 순차 탐색
- 각 에이전트 탐색 목표:
  1. 변경이 필요한 파일 목록 (2-A, 2-B에서 식별된 고위험/Hotspot 파일 포함)
  2. 현재 문제 패턴 (구체적인 코드 냄새)
  3. 다른 도메인과의 의존 방향
  4. 기존 테스트 커버리지 현황 (없음 / 부분 / 충분)

탐색 중 Step 1에서 정의하지 않은 새 도메인이 발견되면:
1. 사용자에게 알리고 도메인 목록 추가 여부를 확인한다
2. 추가 확정 시 해당 도메인에 대해 2-A/2-B/2-C를 재실행한다
3. 결과를 기존 계획에 통합한다

탐색 완료 후 아래 매핑 규칙에 따라 결과를 plan.md와 task 파일로 옮긴다.

| 탐색 결과 | 반영 위치 |
|----------|---------|
| 2-A Fan-out 높은 파일 | 의존 관계 다이어그램 + Phase 후반 배치 |
| 2-A Fan-in 높은 파일 | 고위험 파일 목록 + 신중 처리 표시 |
| 2-B Hotspot | 분석 요약 섹션 + Phase 앞쪽 배치 |
| 2-C 변경 대상 파일 | task 파일 체크리스트 |
| 2-C 문제 패턴 | task 파일 상세 섹션 |
| 2-C 의존 방향 | 2-A 의존 관계 다이어그램 보완 |
| 2-C 테스트 없는 파일 | task 파일 해당 항목에 "테스트 작성 선행" 표시 |

**Fan-out 높음 + Hotspot 충돌 시**: task를 두 개로 분리한다.
- `NN-N-a`: 의존성 격리 (인터페이스 추출 / Fan-out 감소) → 현재 Phase
- `NN-N-b`: 핵심 리팩토링 → 다음 Phase

---

### Step 3. 계획 초안 작성 후 사용자 확인

아래 내용을 보여주고 사용자가 아래 항목을 검토할 수 있도록 한다:

- `plan.md` 전체 내용
- task 파일별 **체크리스트 항목 목록만** 표시 (상세 섹션은 생략) — 파일명, 항목 수, 각 항목 한 줄

**검토 체크리스트** (사용자가 확인해야 할 항목):
1. Phase 순서가 의존 관계 방향과 일치하는가
2. 도메인 간 선행/후행 관계가 누락 없이 반영됐는가
3. Phase 0 대상에 테스트 현황 "없음/부분"인 도메인이 모두 포함됐는가
4. 각 Phase 작업량이 한쪽에 과도하게 몰리지 않는가

수정 요청이 있으면 반영한 뒤 파일을 생성한다.

---

### Step 4. 파일 생성

`.claude/plan/refactor/` 디렉토리에 아래 구조로 생성한다:

```
.claude/plan/refactor/
├── plan.md
├── analysis/
│   ├── dependency.md   (2-A 결과: Fan-out/Fan-in 목록)
│   └── hotspots.md     (2-B 결과: Hotspot 목록 + 판정)
└── tasks/
    ├── 01-<도메인>.md
    ├── 02-<도메인>.md
    └── ...
```

**작업 재개 시** (plan.md + analysis/ 파일이 이미 존재하는 경우):
1. Step 1, 2를 건너뛴다
2. `analysis/dependency.md`, `analysis/hotspots.md`를 읽어 컨텍스트를 복원한다
3. 각 task 파일의 체크리스트를 확인해 미완료 항목부터 이어서 진행한다

---

## 작성 규칙

**analysis/dependency.md**
- 상단에 분석 일시, 기준(상위 20%) 명시
- 섹션: Fan-out 높은 파일 (파일/import 수/영향 도메인), Fan-in 높은 파일 (파일/참조 수/영향 도메인), 도메인 간 선행/후행 관계 (ASCII)
- 새 도메인 발견으로 재실행 시 기존 파일을 덮어쓴다

**analysis/hotspots.md**
- 상단에 분석 일시, 분석 방식(git 기반 / 정적 분석), 기준 명시
- 섹션: Hotspot 목록 (파일/변경 빈도/라인 수/판정/관련 도메인), 도메인별 우선순위 (도메인/우선순위/근거)
- 새 도메인 발견으로 재실행 시 기존 파일을 덮어쓴다

**plan.md**
- 섹션 순서: 현황 요약 → 분석 요약 → 도메인별 작업 현황 → 실행 원칙 → 실행 순서 → 의존 관계 → 검증 방법 → 핵심 파일 목록 → 보류 요약
- 도메인별 작업 현황 테이블: `#`, `도메인`, `파일`, `테스트 현황`, `상태` 컬럼 포함
- 도메인 번호는 `01`부터 두 자리 숫자로 시작
- 상태: `미완료 (0/N)` / `부분 완료 (n/N)` / `완료 (N/N)`
- 실행 순서 Phase 0은 항상 "테스트 안전망 구축"으로 고정. 모든 도메인 테스트가 "충분"이면 생략 표시
- Phase 0 테스트 작성 전략: 특성화 테스트(기본) + BDD(user-facing 보완) + 단위 테스트(Phase 1 이후)
- Phase 구분: 의존 관계 기준으로 묶음
- 의존 관계는 ASCII 다이어그램으로 표현 (이모지 금지)
- 검증 방법: 빌드/컴파일, 테스트 통과, 기능 동작 확인 세 종류 명시

**task 파일**
- 파일명: `NN-<도메인>.md` (도메인명 영문 소문자 + 하이픈)
- 상단 헤더 필드: 우선순위, 선행 조건, 테스트 현황
- 섹션 순서: 진행 현황 → 상세
- 진행 현황 첫 항목은 `NN-0. 특성화 테스트 작성` — 테스트 현황이 "충분"이면 생략
  - NN-0 상세: 대상 파일, 작성 방식(input/output 고정), user-facing 시나리오 시 BDD 보완
- 각 항목: `- [x]` (완료) / `- [ ]` (미완료 또는 보류)
- 보류 항목에는 **보류 이유** 명시
- 이모지 금지 — 체크박스만 사용
- 상세 섹션은 항목별로 현재 문제 + 변경 방향 기술
- `NN-N-a/b`로 분리된 항목은 상세 섹션 첫 줄에 `격리 작업` 또는 `핵심 리팩토링` 중 하나를 명시
- 우선순위 결정 기준 (2-A, 2-B 분석 결과 기반):
  - **높음** — 도메인 내 Hotspot 파일 1개 이상, 또는 다른 도메인의 선행 조건
  - **중간** — Hotspot은 없지만 변경 빈도 높은 파일 포함, 또는 다른 도메인과 의존 관계 있음
  - **낮음** — 안정적 파일만 포함, 독립 진행 가능

**공통**
- 작업 완료 시: Claude가 즉시 task 파일 체크박스 + plan.md 상태 칸을 동시 업데이트한다
- 작업 중 보류가 발생하면 plan.md 보류 요약 섹션에 추가
